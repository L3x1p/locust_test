# Анализ точки поломки (bottleneck) по отчётам Locust

## При каком количестве пользователей — bottleneck

**Около 80 виртуальных пользователей.**

По `report_stats_history.csv`:
- При **80 пользователях** p95 впервые превысил **5000 ms** (5 с): в строке с timestamp 1771577089 зафиксировано **95% = 5000**, затем 5100 ms.

Тест остановился по правилу **«p95 > 5 с»** (порог в режиме FIND_BREAKING_POINT).

---

## Почему (причина)

1. **Ошибок не было**  
   В `report_failures.csv` и `report_exceptions.csv` записей нет → остановка не из‑за ошибок (failure count не достиг порога).

2. **Причина — задержка (p95)**  
   Сработало правило: **p95 времени ответа > 5 с**.  
   В `report_stats.csv` по Aggregated:
   - **Median Response Time:** 10 000 ms (10 с)
   - **95%:** 14 000 ms (14 с)  
   То есть при текущей нагрузке и хвосте запросов система не укладывается в 5 с.

3. **Что это значит**  
   При ~80 одновременных пользователях и ~35–37 RPS:
   - API + vLLM перестают успевать отвечать в пределах 5 с для 95% запросов.
   - Скорее всего ограничение по ресурсам (vLLM/GPU или очередь запросов), а не по сетевым ошибкам.

---

## Итог

| Параметр              | Значение        |
|-----------------------|-----------------|
| **Число пользователей** | ~80             |
| **Причина остановки**  | p95 > 5 с       |
| **Ошибки (failures)**   | 0               |
| **Итоговый p95**       | 14 с (в report_stats) |
| **Итоговый RPS**       | ~31             |

**Вывод:** Точка поломки по правилу «p95 ≤ 5 с» достигается при **~80 пользователях**. Дальнейшее увеличение нагрузки ведёт к росту задержек (медиана и p95), без появления ошибок в этом прогоне.
